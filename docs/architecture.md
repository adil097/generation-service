# Архитектура сервиса генерации

Основание: [тестовое задание](../TASK.md).

Утверждённый стек: Python, FastAPI, Uvicorn, PostgreSQL, SQLAlchemy с
асинхронным расширением и asyncpg, Alembic, HTTPX, Pydantic Settings,
Pytest, pytest-asyncio, Docker и Docker Compose.

Статус реализации и результаты проверок ведутся в [PLAN.md](../PLAN.md).
Схема реализована миграциями Alembic `0001`–`0002`; каталог создаётся миграцией,
демонстрационные пользователи — отдельной идемпотентной командой.
Роли `generation_migrator`, `generation_app`, `generation_provider` создаются
административным заданием до миграций. Миграции назначают права на таблицы;
API и провайдеры подключаются своими ограниченными ролями.

## 1. Сущности и ограничения

Этот раздел определяет модель данных и правила её целостности. Обработка
конкуренции описана в разделе 2, завершение попытки — в разделе 3.
Поздние результаты описаны в разделе 4, отправка запросов и восстановление
после падения процесса — в разделе 5.

### Общие соглашения

- Состояние сервиса хранится в PostgreSQL и доступно всем процессам.
- Токены — целые числа типа `BIGINT`. Дробные значения не допускаются.
- Время хранится в `TIMESTAMPTZ`; приложение использует UTC.
- Все перечисленные поля обязательны, кроме явно обозначенных как `NULL`.
- Допустимые значения статусов и типов операций ограничиваются `CHECK`.
- Внешние ключи используют `ON DELETE RESTRICT`: удаление связанных данных
  не должно уничтожать финансовую историю или историю генерации.

### 1.1. Пользователь — `users`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `BIGINT`, PK | Идентификатор пользователя, передаваемый в API |
| `created_at` | `TIMESTAMPTZ` | Время создания |

**Баланс вычисляется по журналу операций**, отдельного поля `users.balance` нет:

```sql
SELECT COALESCE(SUM(amount), 0)
FROM ledger_entries
WHERE user_id = :user_id;
```

Таким образом, баланс по определению равен сумме журнала: отдельное изменение
баланса без строки журнала невозможно. Для объёма тестового задания вычисление
суммы проще, чем поддержка согласованности двух копий одного значения.

Пользователь без записей журнала имеет нулевой баланс. Начальные токены
тестовых пользователей также оформляются записями журнала.

Инварианты: баланс неотрицателен; у пользователя не более трёх активных задач.
Это ограничения на несколько строк, их обеспечение описано в пункте 1.8.

### 1.2. Провайдер — `providers`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `name` | `TEXT`, PK | Имя провайдера: `alpha` или `beta` |

В начальной миграции создаются две записи. URL провайдеров и секреты HMAC
задаются настройками окружения через Pydantic Settings. Секреты в таблицах
каталога не хранятся.

### 1.3. Модель генерации — `generation_models`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `BIGINT`, PK | Внутренний идентификатор |
| `slug` | `TEXT`, UNIQUE | Имя модели в API |
| `price_tokens` | `BIGINT` | Цена генерации |

Ограничения БД: `price_tokens > 0`; `slug` непустой и уникальный.

Начальный каталог:

| `slug` | `price_tokens` |
| --- | --- |
| `image-fast` | 2 |
| `video-long` | 25 |

### 1.4. Нога модели — `model_legs`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `BIGINT`, PK | Идентификатор ноги |
| `model_id` | `BIGINT`, FK | Модель генерации |
| `provider_name` | `TEXT`, FK | Провайдер |
| `priority` | `INTEGER` | Порядок выбора: меньшее значение раньше |
| `max_ref_images` | `INTEGER` | Максимальное количество референсов |
| `skip_on_moderation` | `BOOLEAN` | Пропускать ногу после отказа по модерации |

Ограничения БД:

- `UNIQUE (model_id, priority)` — порядок ног внутри модели однозначен.
- `priority > 0`, `max_ref_images >= 0`.
- `model_id` ссылается на `generation_models.id`, `provider_name` — на
  `providers.name`.

Начальные записи:

| Модель | Приоритет | Провайдер | Максимум референсов | `skip_on_moderation` |
| --- | --- | --- | --- | --- |
| `image-fast` | 1 | `alpha` | 4 | `false` |
| `image-fast` | 2 | `beta` | 10 | `false` |
| `video-long` | 1 | `beta` | 2 | `false` |
| `video-long` | 2 | `alpha` | 1 | `true` |

В рамках задания каталог задаётся миграцией и не редактируется во время
обработки задач. Это сохраняет смысл ссылок на ноги и порядок их обхода.

### 1.5. Задача генерации — `generation_tasks`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID`, PK | Идентификатор `task_id` из API |
| `user_id` | `BIGINT`, FK | Владелец задачи |
| `model_id` | `BIGINT`, FK | Выбранная модель |
| `price_tokens` | `BIGINT` | Цена, зафиксированная при создании |
| `prompt` | `TEXT` | Текст запроса |
| `ref_images` | `JSONB` | Массив строк со ссылками на референсы |
| `status` | `TEXT` | `queued`, `processing`, `completed` или `failed` |
| `result_url` | `TEXT`, NULL | Ссылка на результат |
| `created_at` | `TIMESTAMPTZ` | Время создания |
| `finished_at` | `TIMESTAMPTZ`, NULL | Время завершения |

Ограничения БД:

- `price_tokens > 0`; возврат рассчитывается по этой цене.
- `user_id` ссылается на `users.id`, `model_id` — на `generation_models.id`.
- `ref_images` является JSON-массивом. Типы его элементов проверяет API.
- `result_url` содержит непустую строку только при `status = 'completed'`;
  в остальных состояниях равен `NULL`.
- `finished_at` заполнен только для `completed` и `failed` и не предшествует
  `created_at`.

Активными считаются задачи в состояниях `queued` и `processing`. Повторный
вызов `POST /generate` создаёт отдельную задачу: идемпотентность этого метода
тестовым заданием не предусмотрена.

### 1.6. Попытка генерации — `generation_attempts`

Попытка — выполнение конкретной задачи на конкретной ноге. Она имеет
собственный идентификатор ещё до обращения к провайдеру.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID`, PK | Внутренний идентификатор попытки |
| `task_id` | `UUID`, FK | Задача генерации |
| `model_id` | `BIGINT` | Модель для проверки согласованности связей |
| `leg_id` | `BIGINT`, FK | Выбранная нога |
| `provider_name` | `TEXT`, FK | Провайдер этой ноги |
| `attempt_number` | `INTEGER` | Порядковый номер попытки внутри задачи |
| `external_id` | `TEXT`, NULL | Идентификатор, возвращённый провайдером |
| `request_payload` | `JSONB` | Неизменяемое тело запроса провайдеру, включая `client_attempt_id` |
| `status` | `TEXT` | `pending`, `awaiting_result`, `completed`, `failed` или `timed_out` |
| `error_type` | `TEXT`, NULL | `technical`, `moderation` или `payload` |
| `error_details` | `TEXT`, NULL | Диагностика: ответ провайдера, HTTP-ошибка или таймаут |
| `created_at` | `TIMESTAMPTZ` | Время создания попытки |
| `sent_at` | `TIMESTAMPTZ`, NULL | Время первой фиксации начала отправки до HTTP-вызова |
| `deadline_at` | `TIMESTAMPTZ`, NULL | Общий срок восстановления отправки и ожидания результата |
| `dispatch_token` | `UUID`, NULL | Текущее право исполнителя на отправку |
| `dispatch_lease_until` | `TIMESTAMPTZ`, NULL | Срок действия этого права |
| `finished_at` | `TIMESTAMPTZ`, NULL | Время завершения попытки |

Ограничения БД:

- `UNIQUE (task_id, attempt_number)`, `attempt_number > 0`.
- `UNIQUE (task_id, leg_id)` — одна нога используется не более одного раза
  в рамках задачи.
- `UNIQUE (provider_name, external_id)` — внешний идентификатор уникален
  в пределах провайдера. Несколько `NULL` до получения ответа допустимы.
- Частичный уникальный индекс по `task_id` для статусов `pending` и
  `awaiting_result` допускает не более одной активной попытки у задачи.
- Составные внешние ключи `(task_id, model_id)` и
  `(leg_id, model_id, provider_name)` гарантируют, что попытка использует
  ногу своей модели и соответствующего провайдера. В родительских таблицах
  создаются необходимые составные `UNIQUE` для этих ссылок.
- `error_type` обязателен для `failed` и `timed_out`, в остальных состояниях
  равен `NULL`. Для `timed_out` используется `technical`.
- `request_payload` является JSON-объектом с обязательным `client_attempt_id`,
  равным строковому представлению `id` попытки.
- `sent_at` и `deadline_at` либо оба `NULL`, либо оба заполнены,
  причём `deadline_at > sent_at`. Для `awaiting_result` оба обязательны.
- `dispatch_token` и `dispatch_lease_until` либо оба `NULL`, либо оба
  заполнены. Заполненная пара разрешена только для `pending` с заполненным
  `sent_at`; срок права на отправку не превышает `deadline_at`.
- `finished_at` заполнен только для `completed`, `failed` и `timed_out`
  и не предшествует `created_at`.

Неизменяемый `request_payload` формируется при создании попытки. Для таблицы
попыток роль приложения получает `UPDATE` только на изменяемые служебные поля,
без права обновления `request_payload`, идентификаторов и принадлежности.
Общее табличное право `UPDATE` ей не выдаётся; миграционная роль отдельная.

Неподходящие и пропущенные ноги не создают попытку. Синхронная ошибка отправки
создаёт запись в истории, поскольку обращение к провайдеру предпринималось.

Текущая нога активной задачи определяется по активной попытке. История
сортируется по `attempt_number`; последняя использованная нога завершённой
задачи определяется по последней попытке. Отдельный указатель на текущую ногу
не хранится.

### 1.7. Журнал операций — `ledger_entries`

Каждая запись отражает одно изменение количества токенов пользователя.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID`, PK | Идентификатор операции |
| `user_id` | `BIGINT`, FK | Пользователь |
| `kind` | `TEXT` | `payment_credit`, `generation_debit` или `generation_refund` |
| `amount` | `BIGINT` | Изменение баланса со знаком |
| `payment_id` | `TEXT`, NULL | Идентификатор подтверждённой оплаты |
| `task_id` | `UUID`, NULL, FK | Задача, вызвавшая списание или возврат |
| `created_at` | `TIMESTAMPTZ` | Время операции |

Ограничения БД:

| Тип операции | Знак `amount` | `payment_id` | `task_id` |
| --- | --- | --- | --- |
| `payment_credit` | `> 0` | Обязателен, непустой | `NULL` |
| `generation_debit` | `< 0` | `NULL` | Обязателен |
| `generation_refund` | `> 0` | `NULL` | Обязателен |

- `UNIQUE (payment_id)` — одна оплата даёт не более одного начисления,
  включая одновременные доставки вебхука.
- `UNIQUE (task_id, kind)` — для задачи допускается не более одного списания
  и не более одного возврата.
- `user_id` ссылается на `users.id`.
- Составной внешний ключ `(task_id, user_id)` ссылается на
  `generation_tasks (id, user_id)`: списание и возврат относятся к владельцу
  задачи. В `generation_tasks` создаётся соответствующий `UNIQUE`.

Журнал используется только для добавления записей. При реализации роль БД,
под которой работает приложение, получит `SELECT` и `INSERT` на журнал,
без `UPDATE` и `DELETE`; миграции выполняются отдельной ролью.

Начисление создаётся только для подтверждённой успешной оплаты. Повторный
`payment_id` с другим пользователем или количеством токенов считается
конфликтом данных и не создаёт новое начисление. Отдельная таблица оплат пока
не требуется: хранение их промежуточных состояний не входит в задание.

### 1.8. Инварианты, требующие транзакционной проверки

Уникальные ограничения обеспечивают «не более одного раза». Чтобы операция
произошла полностью и была согласована с состоянием задачи, нужны также
транзакции приложения. Следующие правила нельзя выразить обычным `CHECK`
одной строки:

| Инвариант | Связанные данные |
| --- | --- |
| Баланс пользователя не становится отрицательным | Все его записи журнала |
| У пользователя не более трёх активных задач | Все его задачи в `queued` и `processing` |
| Каждая созданная задача имеет ровно одно списание | Задача и её запись `generation_debit` |
| Сумма списания равна `-price_tokens` задачи | Задача и журнал |
| Каждая задача `failed` имеет ровно один полный возврат | Задача, списание и возврат |
| Сумма возврата равна исходному списанию по модулю | Задача и журнал |
| Задача `completed` не имеет возврата | Задача и журнал |
| Нога принимает количество референсов задачи | Задача, нога и попытка |
| У завершённой задачи нет активной попытки | Задача и её попытки |

При неподходящем количестве референсов, недостаточном балансе или превышении
лимита активных задач новая задача и списание не сохраняются.

Механизм сериализации конкурирующих операций и границы транзакций
описаны в разделе 2. Одних предварительных проверок в Python
недостаточно для выполнения этих правил в четырёх процессах.

### 1.9. Индексы для основных запросов

Помимо индексов первичных и уникальных ключей нужны:

- `ledger_entries (user_id, created_at DESC, id)` — чтение баланса
  и последних операций пользователя.
- Частичный индекс `generation_tasks (user_id)` для статусов `queued`
  и `processing` — подсчёт активных задач.
- Частичный индекс `generation_attempts (deadline_at)` для статусов
  `pending` и `awaiting_result` при `deadline_at IS NOT NULL` — поиск
  просроченных попыток, включая незавершённую отправку.
- Частичный индекс `generation_attempts (created_at, id)` для статуса
  `pending` — поиск кандидатов на отправку и восстановление.

История попыток использует индекс ограничения
`UNIQUE (task_id, attempt_number)`.

Справка по механизмам БД:
[ограничения PostgreSQL](https://www.postgresql.org/docs/17/ddl-constraints.html),
[частичные индексы PostgreSQL](https://www.postgresql.org/docs/17/indexes-partial.html).

### 1.10. Состояние фейковых провайдеров — `fake_providers.provider_tasks`

Фейковые провайдеры также сохраняют свои задачи в PostgreSQL, в отдельной
схеме и под ролью с доступом к этой схеме. Основной сервис взаимодействует
с ними только через HTTP. Таблица хранит:

- `provider_name`, `client_attempt_id`, `external_id` и исходный JSON-запрос;
- состояние `accepted`, `completed` или `failed`, время готовности результата
  и выбранный при приёме сценарий поведения;
- результат и сериализованное сырое тело вебхука после завершения генерации;
- срок следующей доставки, её временный токен, срок действия токена
  и время успешной доставки.

В реализации ключ `(provider_name, client_attempt_id)` является первичным.
Сценарий хранится в `scenario` (`JSONB`), готовность — в `ready_at`,
завершение — в `finished_at`, сырые байты — в `webhook_body`,
число успешных доставок — в `successful_deliveries`. Состояние `accepted`
не содержит результата и вебхука; терминальное состояние содержит время
завершения, тело вебхука и соответствующую пару результата/ошибки.
Индексы по `ready_at` и `next_delivery_at` обслуживают фоновые циклы.

В БД обязательны `UNIQUE (provider_name, client_attempt_id)` и
`UNIQUE (provider_name, external_id)`. Токен доставки и срок его действия
либо оба `NULL`, либо оба заполнены. Тело вебхука сохраняется как `BYTEA`,
чтобы повторно отправлять те же байты. Протокол работы описан в разделе 5.

## 2. Обработка конкуренции

### 2.1. Уровень изоляции и область действия блокировок

Для изменяющих операций используем `READ COMMITTED` и явные блокировки строк
через `SELECT ... FOR UPDATE`. Блокировка действует до `COMMIT` или `ROLLBACK`
и координирует все процессы, подключённые к одной БД.

Каждая бизнес-операция получает отдельную `AsyncSession` и транзакцию.
Одна сессия не используется одновременно несколькими запросами или фоновыми
задачами. Успешный HTTP-ответ об изменении данных отправляется после `COMMIT`.

Блокировка пользователя служит общим правилом для всех операций, которые
меняют его журнал или состояние его задач. Даже при вычисляемом балансе
блокируем существующую строку `users`, а не результат `SUM`: эта строка есть
и у пользователя с пустым журналом.

Это протокол приложения: блокировка `users` сама по себе не запрещает другим
транзакциям вставлять строки в журнал или таблицу задач. Все пути записи,
включая начальное наполнение данных, обязаны соблюдать этот протокол.

После получения блокировки баланс и число активных задач читаются отдельными
SQL-запросами. В `READ COMMITTED` эти запросы видят изменения, зафиксированные
предыдущим владельцем блокировки. Нельзя вычислять баланс до ожидания блокировки
и затем использовать старое значение; по той же причине не объединяем захват
блокировки и агрегатные проверки в один запрос или CTE.

### 2.2. Единый порядок блокировок

Все изменяющие операции соблюдают порядок:

```text
users → generation_tasks → generation_attempts → запись в ledger_entries
```

1. Сначала блокируется пользователь.
2. Если операция относится к существующей задаче, затем блокируется задача.
3. Если изменяется существующая попытка, затем блокируется попытка.
4. Записи журнала добавляются после получения необходимых блокировок.

Начальный поиск по `task_id` или паре `(provider_name, external_id)` может
выполняться без блокировки, чтобы определить владельца. Полученные данные
используются только для поиска: решение принимается после блокировок и
повторного чтения актуального состояния. Владелец задачи и принадлежность
попытки задаче после создания не меняются.

Все обработчики результатов, включая успешный результат, сначала блокируют
пользователя. Это сериализует короткие операции по задачам одного пользователя
и позволяет использовать один порядок для успеха, отказа и возврата. Для лимита
в три активные задачи такая простота оправдана. Разные пользователи обычно
обрабатываются независимо; общий `payment_id` дополнительно координируется
уникальным ограничением.

Не допускается сначала захватить задачу или попытку, а затем ждать блокировку
пользователя. Одна транзакция обрабатывает одну задачу или одну оплату.

### 2.3. Создание генерации — `POST /generate`

До блокировок проверяем форму запроса, существование модели и наличие хотя бы
одной подходящей ноги. Каталог во время работы не меняется. Если подходящей
ноги нет, возвращаем 400 без создания задачи и списания.

В одной транзакции:

1. Блокируем строку пользователя через `FOR UPDATE`. Пользователь должен
   существовать; создание пользователей этим методом не предусмотрено.
2. Отдельным запросом читаем сумму его журнала.
3. Отдельным запросом считаем его задачи в `queued` и `processing`.
4. При недостаточном балансе откатываем транзакцию и возвращаем 402. Если
   баланс достаточен, но уже есть три активные задачи, возвращаем 429.
5. Создаём задачу с зафиксированной ценой, запись `generation_debit` на
   отрицательную величину этой цены и первую подходящую попытку `pending`.
6. Фиксируем все три записи одним `COMMIT`.

Первые запросы транзакции имеют следующую форму:

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;

SELECT id FROM users WHERE id = :user_id FOR UPDATE;

SELECT COALESCE(SUM(amount), 0)
FROM ledger_entries
WHERE user_id = :user_id;

SELECT COUNT(*)
FROM generation_tasks
WHERE user_id = :user_id
  AND status IN ('queued', 'processing');
```

Следующий запрос генерации этого пользователя ждёт завершения транзакции,
затем пересчитывает баланс и число задач. Поэтому два запроса не могут
потратить одни и те же токены или одновременно занять последнее свободное место.

Реализация — `GenerationService.create(GenerationRequest(...))` в
`generation_service.services.generation`. Запрос сохраняет референсы неизменяемым
кортежем; цена берётся только из каталога. Пустые prompt/model_slug и пустые
элементы референсов отклоняются валидацией. После записи задачи финансовый слой
добавляет списание, затем создаётся попытка. Ошибка вставки попытки откатывает
задачу и журнал. `CALLBACK_BASE_URL` задаёт доступный провайдерам адрес API
(в Compose — `http://api:8000`); полный callback URL фиксируется в запросе попытки.
Результат содержит `task_id` и `attempt_id` только после успешного `COMMIT`.
Отправка и подключение HTTP-метода выполняются на этапах 8 и 9.

### 2.4. Начисление оплаты — `POST /webhooks/payments`

Подпись по сырому телу, структура события и положительное целое количество
токенов проверяются до начала транзакции. Событие без подтверждённой успешной
оплаты не создаёт начисление.

В реализованном финансовом контракте `PaymentEvent.status` принимает
`success`, `pending` и `failed`; начисление выполняется только для `success`.
Валидация строго проверяет целые `tokens` в диапазоне `1..2^63-1` и непустой
`payment_id`. HTTP-подпись проверит адаптер на этапе 9.

Для подтверждённой оплаты в одной транзакции:

1. Блокируем пользователя.
2. Вставляем `payment_credit` через
   `INSERT ... ON CONFLICT (payment_id) DO NOTHING RETURNING id`.
3. Если строка вставлена, начисление выполнено. Если строка не вставлена,
   отдельным запросом читаем существующую запись и сравниваем `user_id`
   и `amount` с событием.
4. Полное совпадение означает уже обработанный дубликат. Несовпадение —
   конфликт данных: возвращаем 409 и не меняем журнал.
5. Для новой оплаты и совпадающего дубликата возвращаем 2xx после `COMMIT`.

Отдельный запрос после `ON CONFLICT` нужен, чтобы увидеть запись, которая
могла быть зафиксирована другой транзакцией во время ожидания уникального
ограничения. Один `payment_id` остаётся уникальным даже при ошибочно
переданных разных `user_id`: блокировки разных пользователей этого не решают,
но уникальное ограничение БД предотвращает второе начисление.

### 2.5. Обработка результата и возврат

Вебхук провайдера, синхронная ошибка отправки и решение сторожа используют
одинаковый порядок блокировок. Подпись вебхука проверяется до транзакции.

В одной транзакции обработчик:

1. Блокирует пользователя, задачу и целевую попытку в установленном порядке.
2. Повторно проверяет статус задачи и попытки. Событие применяется только
   к текущей активной попытке незавершённой задачи.
3. Если задача или попытка уже завершены, подтверждает повторный или
   устаревший вебхук без изменения результата, истории и журнала.
4. Принимает результат либо завершает попытку с ошибкой. При переходе на
   следующую ногу закрывает текущую попытку и создаёт следующую `pending`
   в этой же транзакции. Старую попытку закрываем до вставки новой, чтобы
   соблюсти уникальный индекс активной попытки.
5. Если задача окончательно завершается ошибкой, переводит её в `failed`
   и добавляет `generation_refund` в этой же транзакции. Размер возврата
   равен сумме исходного списания по модулю.
6. Выполняет `COMMIT` перед подтверждением обработки.

Возврат добавляется через `ON CONFLICT (task_id, kind) DO NOTHING RETURNING id`.
При конфликте проверяем, что существующий возврат относится к тому же
пользователю и имеет ожидаемую сумму. Расхождение означает нарушение
целостности: транзакция откатывается, событие не подтверждается как успешно
обработанное. При штатной обработке дубликат останавливается уже на проверке
завершённой задачи; уникальный ключ остаётся дополнительной защитой.

При десяти одновременных отказах на последней ноге первый обработчик завершает
задачу и создаёт возврат. Остальные после ожидания видят завершённую задачу
и ничего не добавляют.

При гонке `completed` и таймаута решение определяется тем, какая транзакция
первой получила блокировки и зафиксировала изменение. Сторож повторно проверяет
срок ожидания под блокировками. Если он уже завершил попытку по таймауту,
её поздний результат не применяется, даже когда задача продолжает выполняться
на следующей ноге. Общий механизм переходов описан в разделе 3;
обоснование правила поздних результатов — в разделе 4.

### 2.6. Несколько сторожей

Каждый процесс может запускать свой цикл сторожа. Поиск просроченных
`awaiting_result` и уже начатых `pending` возвращает кандидатов, но ещё
не даёт права изменять их. У таких `pending` уже заполнен `deadline_at`.

Для каждого кандидата открывается отдельная короткая транзакция:

1. Захватываем пользователя через `FOR UPDATE SKIP LOCKED`. Если он уже занят,
   откладываем кандидата до следующего прохода.
2. Захватываем задачу через `FOR UPDATE SKIP LOCKED`, затем попытку тем же
   способом. Если строка пропущена или исчезла, завершаем транзакцию без
   изменений и освобождаем уже полученные блокировки.
3. Повторно проверяем, что задача активна, попытка всё ещё текущая, имеет
   статус `pending` или `awaiting_result`, её `deadline_at` заполнен
   и `deadline_at <= clock_timestamp()`.
4. Если условия сохраняются, применяем таймаут по пункту 2.5 и фиксируем
   изменение; иначе завершаем транзакцию без изменений.

Эта транзакция выполняется внутри `finish_attempt` из раздела 3.
Сторож передаёт кандидата в операцию без внешней транзакции с уже захваченными
блокировками.

Порядок захвата сохраняется и для сторожа. Начинать с блокировки просроченных
попыток, а затем получать пользователя нельзя. `SKIP LOCKED` используется
только при фоновом распределении кандидатов; пропуск занятой строки не означает
отсутствие задачи или истечение её срока.

Два сторожа могут найти одного кандидата, но только один применит к нему
таймаут. Сканирование периодически повторяется: пропущенная строка не теряется.
HTTP-запрос к следующему провайдеру не входит в транзакцию сторожа.

### 2.7. Сеть, ошибки транзакций и чтение данных

HTTP-вызовы провайдеров выполняются после освобождения блокировок. Ожидание
ответа провайдера не должно удерживать пользовательскую транзакцию.
При сохранении ответа отправки заново получаем блокировки и проверяем,
что попытка ещё актуальна: за время HTTP-вызова другой обработчик мог
изменить её состояние.

Блокировка строки защищает изменение состояния только до конца транзакции.
Она сама по себе не даёт исполнителю исключительного права на последующий
HTTP-вызов. Постоянное право на отправку `pending`, его срок действия,
идемпотентность запроса провайдеру и восстановление после падения между
`COMMIT` и HTTP-вызовом обеспечиваются протоколом из раздела 5.

При падении процесса до фиксации PostgreSQL откатывает незавершённую
транзакцию и освобождает её блокировки после завершения соединения. После
успешного `COMMIT`, но до ответа на вебхук, повторная доставка обнаруживает
уже записанный результат. Это сохраняет однократность финансового эффекта;
для обработки события после падения до `COMMIT` нужна повторная доставка.

Взаимная блокировка (`40P01`) или ошибка сериализации (`40001`) приводит
к откату и ограниченному повтору всей транзакции с повторным чтением данных.
Сетевые запросы в такой повтор не входят. Время ожидания блокировок
ограничивается `lock_timeout`; при исчерпании ожидания или повторов
транзакция откатывается, а API возвращает 503. Такой сбой не превращается
в отказ генерации и не создаёт возврат токенов. Ответ 503 означает,
что вебхук не подтверждён.

Обрыв соединения во время `COMMIT` может оставить результат фиксации
неизвестным клиенту. Идемпотентные вебхуки допускают повтор с тем же
идентификатором. Для `POST /generate` автоматический повтор при неизвестном
результате фиксации не выполняется: у метода нет ключа идемпотентности,
а повтор способен создать вторую задачу.

Обычные `GET` не требуют блокировок строк. Баланс и последние операции,
а также задача и её история должны читаться из одного согласованного снимка:
одним SQL-запросом либо несколькими запросами внутри короткой read-only
транзакции `REPEATABLE READ`.

Финансовый слой реализован в `generation_service.services.finance`.
`FinancialService` управляет транзакциями оплаты и чтения баланса;
`debit_generation` и `refund_generation` включаются в транзакцию создания
или завершения задачи, сами не фиксируя её. `TransactionRunner` использует
отдельную сессию на попытку, `lock_timeout = 5000ms` и максимум три попытки
только для `40P01`/`40001`. Баланс и журнал читаются в read-only
`REPEATABLE READ`. Функции блокировок используют скалярные SQL-запросы,
чтобы после ожидания не принимать решения по ранее загруженному ORM-объекту.

### 2.8. Сценарии для проверки реализации

| Одновременные события | Ожидаемый результат |
| --- | --- |
| Два запроса при балансе на одну генерацию | Одна задача и одно списание; второй запрос получает 402 |
| Несколько запросов при двух активных задачах и достаточном балансе | Создаётся только третья активная задача; остальные получают 429 |
| Двадцать одинаковых вебхуков оплаты | Одна запись `payment_credit` |
| Одинаковый `payment_id` с разными пользователями или суммами | Одно начисление; несовпадающее событие получает 409 |
| Десять отказов последней ноги | Одна финализация задачи и одна запись `generation_refund` |
| Два сторожа обрабатывают одну просроченную попытку | Один переход на следующую ногу либо один возврат |
| Вебхук и сторож завершают одну попытку | Применяется только одно решение; результат и возврат не сосуществуют |
| Старый вебхук приходит при выполнении следующей ноги | Новая попытка и её результат не изменяются |
| Процесс падает до `COMMIT` или после него до ответа на вебхук | Повторная доставка приводит к одному финансовому эффекту |

Эти сценарии проверяются на настоящем PostgreSQL через независимые соединения
и транзакции. Проверка только внутри одного процесса с общей сессией не
подтверждает работу принятого протокола.

[блокировки строк и взаимные блокировки](https://www.postgresql.org/docs/17/explicit-locking.html),
[уровни изоляции и видимость `ON CONFLICT`](https://www.postgresql.org/docs/17/transaction-iso.html),
[`SELECT` и `SKIP LOCKED`](https://www.postgresql.org/docs/17/sql-select.html),
[`clock_timestamp()`](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT),
[`AsyncSession` и конкурентные задачи](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks).

## 3. Единый механизм завершения попытки

### 3.1. Одна бизнес-операция для всех источников

Все результаты обрабатываются операцией `finish_attempt(command)`.
Она получает нормализованное событие и в одной транзакции завершает текущую
попытку, затем завершает задачу либо создаёт следующую попытку.

Вебхук, обработчик HTTP-ошибки и сторож только подготавливают команду.
Они не выбирают следующую ногу, не меняют конечные статусы и не создают возврат
самостоятельно. Успешный вебхук также проходит через эту операцию, чтобы
успех и отказ конкурировали по одним правилам.

Операция владеет транзакцией и использует порядок блокировок из раздела 2.
Для вызова сторожем поддерживается режим `skip_locked`: невозможность
получить любую из блокировок означает `deferred`, завершение транзакции
без изменений и повтор в следующем проходе. Для вебхуков и ошибок отправки
используется обычное ожидание блокировок с установленным `lock_timeout`.

HTTP-запросы и ожидание провайдера внутри `finish_attempt` не выполняются.

### 3.2. Нормализованная команда

Общие поля команды:

| Поле | Назначение |
| --- | --- |
| `attempt_id` | Сохранённый внутренний идентификатор конкретной попытки |
| `source` | `provider_webhook`, `dispatch_error` или `watchdog` |
| `outcome` | `completed`, `failed` или `timeout` |
| `provider_name` | Провайдер, к которому относится событие |
| `external_id` | Внешний идентификатор для вебхука; для других источников может отсутствовать |
| `dispatch_token` | Токен актуального исполнителя, обязателен только для `dispatch_error` |
| `result_url` | Непустая ссылка, только для `completed` |
| `error_type` | `technical`, `moderation` или `payload`, только для `failed` |
| `error_details` | Необязательная диагностика отказа |

Команда является внутренним контрактом, а не доверенным телом HTTP-запроса.
Адаптер вебхука проверяет подпись, структуру события и принадлежность провайдеру,
затем устанавливает соответствие конкретной попытке. Если `external_id` уже
сохранён, он должен совпадать с идентификатором события.

Ранний вебхук, когда ответ `202` ещё не сохранён, сопоставляется по подписанному
`client_attempt_id` согласно разделу 5. До установления достоверного соответствия
команда не применяется. Нельзя подставлять текущую попытку задачи вместо
конкретной попытки, от которой пришёл результат.

При достоверно сопоставленном раннем вебхуке ещё отсутствующий `external_id`
сохраняется в попытке в той же транзакции, что и её завершение. Уже сохранённый
внешний идентификатор другим значением не заменяется.

Несогласованные сочетания полей отклоняются до изменения данных: например,
`completed` без ссылки или `failed` без допустимого типа ошибки. Ошибка
валидации вебхука не становится ошибкой генерации и не вызывает возврат.

Нормализация источников:

| Источник | Событие | Команда | Итоговый статус попытки |
| --- | --- | --- | --- |
| Вебхук | `completed` со ссылкой | `completed` | `completed` |
| Вебхук | `failed` с допустимым типом ошибки | `failed` с исходным `error_type` | `failed` |
| Отправка | HTTP 5xx | `failed`, `technical` | `failed` |
| Отправка | Таймаут HTTP или ошибка соединения | `failed`, `technical` | `failed` |
| Сторож | Истёк общий срок начатой отправки и ожидания вебхука | `timeout` | `timed_out`, `error_type = 'technical'` |

Тип `payload` выставляется по явному отказу провайдера; произвольный HTTP 4xx
нельзя автоматически считать таким отказом. Ответ `202` подтверждает приём
запроса и не вызывает завершение попытки.

### 3.3. Проверка применимости под блокировками

Получив блокировки пользователя, задачи и попытки, операция заново читает
актуальные данные и проверяет:

1. Задача находится в `queued` или `processing`.
2. Целевая попытка принадлежит задаче и является её единственной активной
   попыткой. Провайдер команды соответствует провайдеру попытки.
3. Источник допускается для текущего состояния попытки:

   | Источник | Допустимое состояние |
   | --- | --- |
   | `provider_webhook` | `awaiting_result` либо начатая отправка `pending` с заполненным `sent_at` |
   | `dispatch_error` | `pending` с заполненным `sent_at`, совпадающим `dispatch_token` и ещё действующим сроком права на отправку |
   | `watchdog` | `pending` или `awaiting_result` с заполненным `deadline_at <= clock_timestamp()` |

Подтверждение актуального выполнения отправки, включая защиту от запоздалого
ответа прежнего исполнителя, описано в разделе 5. Поля `sent_at` для такого
подтверждения недостаточно.

Терминальное состояние задачи или попытки означает `ignored`: повторное
событие ничего не меняет. Это относится и к противоречивому повтору, например
`failed` после принятого `completed`. Диагностика такого события может попасть
в лог, но уже сохранённая история попытки не переписывается.

Если срок ожидания ещё не истёк или событие отправки уже неактуально, результат
также `ignored` с соответствующей причиной. Неизвестная попытка, неверная
принадлежность провайдеру и недостоверная корреляция являются ошибками входного
события, а не успешно обработанными дубликатами.

До применения изменения проверяется финансовая основа задачи: существует
исходное списание её владельцу на `-price_tokens`, а возврат для активной
задачи отсутствует. Нарушение означает ошибку целостности и откат транзакции.
Оно не нормализуется в `technical` и не запускает обход провайдеров.

### 3.4. Завершение попытки и задачи

После проверок операция получает из БД одно значение времени `applied_at`
и использует его для времени завершения попытки, а при финализации — и задачи.
Время из входящего вебхука не определяет порядок обработки.

| Исход | Изменение текущей попытки | Дальнейшее действие |
| --- | --- | --- |
| `completed` | `status = 'completed'`, заполнить `finished_at`, поля ошибки оставить `NULL` | Задача `completed`, сохранить `result_url` и `finished_at`; возврата нет |
| `failed`, `technical` | `status = 'failed'`, сохранить ошибку и `finished_at` | Найти следующую подходящую ногу |
| `failed`, `moderation` | `status = 'failed'`, сохранить ошибку и `finished_at` | Найти следующую подходящую ногу с учётом `skip_on_moderation` |
| `failed`, `payload` | `status = 'failed'`, сохранить ошибку и `finished_at` | Сразу завершить задачу ошибкой и вернуть токены |
| `timeout` | `status = 'timed_out'`, `error_type = 'technical'`, сохранить причину и `finished_at` | Найти следующую подходящую ногу |

Если следующая нога найдена, текущая попытка закрывается до вставки новой.
Это порядок SQL-операций внутри транзакции, который должен сохраняться
и при использовании ORM, чтобы не нарушить уникальность активной попытки.

Новая попытка создаётся с новым UUID, `status = 'pending'` и
`attempt_number = previous.attempt_number + 1`. Поля `external_id`, `sent_at`,
`deadline_at`, `dispatch_token`, `dispatch_lease_until`, `finished_at` и поля
ошибки остаются `NULL`. Неизменяемый `request_payload` создаётся сразу.
Задача переходит в `queued`, `result_url` и `finished_at` остаются `NULL`.
Переход к отправке
новой попытки и состояние `processing` относятся к механизму отправки.

Переход на другую ногу не создаёт новой задачи или дополнительного списания.
Задача остаётся активной и продолжает занимать одно из трёх мест пользователя.

Если подходящей следующей ноги нет либо получен `payload`, операция выполняет
финализацию с возвратом по пункту 3.6. Все изменения становятся видимыми одним
`COMMIT`; промежуточного состояния с закрытой попыткой и потерянным продолжением
после успешной фиксации быть не должно.

При любом завершении текущей попытки её `dispatch_token` и
`dispatch_lease_until` очищаются. Исходные `sent_at` и `deadline_at`
сохраняются в истории.

### 3.5. Выбор следующей ноги

Выбор выполняется внутри той же транзакции по неизменяемому каталогу:

1. Берём ноги той же модели с `priority` больше приоритета завершённой ноги.
2. Оставляем ноги, у которых `max_ref_images >= len(task.ref_images)`.
3. Исключаем ноги, для которых у задачи уже есть попытка.
4. Если текущая ошибка — `moderation`, исключаем ноги с
   `skip_on_moderation = true`.
5. Выбираем оставшуюся ногу с наименьшим `priority`. Если список пуст,
   задача завершается с возвратом.

При `payload` поиск не выполняется. Таймаут и синхронная ошибка используют
правило `technical`. Повторная отправка на ту же ногу как новая попытка
не предусмотрена.

Пропуск ноги по количеству референсов или модерации не создаёт попытку
и не изменяет причину исходного отказа. Флаг модерации действует на поиск
после последнего фактического отказа: если выбранная следующая нога затем
отказала по `technical`, последующий поиск выполняется уже по `technical`.

Примеры из начального каталога:

| Ситуация | Решение |
| --- | --- |
| `image-fast`, 3 референса, отказ `alpha` по `technical` | Попытка на `beta` |
| `image-fast`, 3 референса, отказ `alpha` по `moderation` | Попытка на `beta`, поскольку у неё флаг выключен |
| `image-fast`, 5 референсов | Первая попытка сразу на `beta`; `alpha` не входит в историю |
| `video-long`, 1 референс, отказ `beta` по `technical` | Попытка на `alpha` |
| `video-long`, 1 референс, отказ `beta` по `moderation` | `alpha` пропускается; задача `failed` с возвратом |
| `video-long`, 2 референса, отказ `beta` по `technical` | `alpha` не принимает столько референсов; задача `failed` с возвратом |
| Любая модель, `payload` на первой ноге | Немедленный `failed` с возвратом, другие ноги не вызываются |

### 3.6. Атомарная финализация с возвратом

Операция выполняет следующие действия в своей текущей транзакции:

1. Убеждается, что исходное списание существует, относится к владельцу задачи
   и соответствует зафиксированной цене.
2. Завершает текущую попытку и переводит задачу в `failed`, заполняя
   `finished_at` и оставляя `result_url = NULL`.
3. Добавляет `generation_refund` на сумму исходного списания по модулю
   по правилам `ON CONFLICT` из пункта 2.5.
4. Фиксирует задачу, попытку и возврат одним `COMMIT`.

Если вставка возврата или другая запись завершается ошибкой, откатываются
также изменения статусов. Повтор сможет обработать всё событие целиком.
Возврат не откладывается в отдельную фоновую задачу.

Сумма берётся из исходного списания и сверяется с `task.price_tokens`.
Текущая цена в каталоге, цена следующей ноги и баланс пользователя на момент
отказа не определяют сумму возврата.

### 3.7. Результат операции и действия вызывающего кода

`finish_attempt` возвращает результат после завершения своей транзакции:

| Результат | Значение | Действие вызывающего кода |
| --- | --- | --- |
| `completed` | Сохранён успешный результат | Подтвердить вебхук |
| `next_attempt_created` | Ошибка сохранена, создана следующая `pending` | После `COMMIT` передать её механизму отправки; вебхук подтвердить |
| `failed_refunded` | Задача завершена ошибкой, возврат записан | Подтвердить вебхук либо завершить обработку ошибки/таймаута |
| `ignored` с причиной | Событие уже применено или неприменимо к текущему состоянию | Для корректного повторного или устаревшего вебхука вернуть 2xx |
| `deferred` | Фоновый обработчик пропустил занятую строку | Повторить в следующем проходе сторожа |

Ошибка валидации, целостности или транзакции не является одним из этих
успешных результатов. Она обрабатывается по правилам API и повторов
из раздела 2.

Результат `next_attempt_created` содержит идентификатор новой попытки.
Уведомление механизма отправки после `COMMIT` может ускорять выполнение,
но сохранённая `pending` должна быть обнаружима и без этого уведомления.
Гарантии доставки и восстановления определены в разделе 5.

### 3.8. Сценарии для проверки реализации

- Параметризованная проверка: вебхук `technical`, HTTP 5xx, таймаут отправки
  и таймаут ожидания выбирают одинаковую следующую ногу. Статус и диагностика
  завершённой попытки сохраняют различие причин.
- `payload` на первой ноге сразу даёт `failed` и один полный возврат,
  даже при наличии подходящей второй ноги.
- `moderation` пропускает все следующие ноги с `skip_on_moderation`;
  пропущенные ноги отсутствуют в истории.
- При выборе каждой следующей ноги заново учитывается количество референсов.
- Переход на вторую ногу оставляет одно исходное списание, две попытки
  в истории и одну активную задачу.
- Два одновременных отказа создают ровно одну следующую попытку; если ног
  больше нет, создают ровно один возврат.
- Успех, отказ и сторож для одной попытки не могут одновременно применить
  разные исходы. Повтор и позднее событие не переписывают историю.
- Ошибка вставки возврата откатывает изменение статусов задачи и попытки.
- `202` не завершает попытку; ошибка валидации вебхука не запускает fallback.

Это требования к будущим тестам реализации. В данном разделе определён
контракт операции; исполняемый код сервиса и тесты пока не созданы.

## 4. Правило позднего результата

### 4.1. Принятая политика

Первое допустимое завершение конкретной попытки, зафиксированное в БД
под общими блокировками, окончательно. Попытка в `completed`, `failed`
или `timed_out` не открывается заново.

После закрытия попытки по таймауту её поздний `completed` подтверждается
ответом 2xx, но не меняет задачу, результат, историю попыток и журнал токенов.
Это правило действует и после возврата, и пока задача выполняется на следующей
ноге. Поздний `failed` обрабатывается так же.

Ответ 2xx означает, что корректное событие принято и больше не требует
доставки. Он не означает, что содержащийся в нём результат применён.
Подпись, структура и принадлежность события конкретной попытке проверяются
так же, как при первом получении. Для недостоверного события это правило
подтверждения не применяется.

### 4.2. Дедлайн и решение сторожа

Само наступление `deadline_at` не меняет состояние строки. Оно даёт сторожу
право завершить попытку, если под блокировками условия таймаута сохраняются.

- Если дедлайн истёк, но сторож ещё не зафиксировал таймаут, корректный
  `completed` текущей активной попытки может быть принят.
- Если сторож первым зафиксировал таймаут, последующий результат этой
  попытки игнорируется, независимо от времени генерации на стороне провайдера.
- Если вебхук первым зафиксировал успех, сторож после получения блокировок
  видит завершённую задачу и не создаёт возврат или следующую попытку.
- Если первый обработчик откатил транзакцию, его незавершённое решение
  не имеет приоритета перед другим обработчиком.

Порядок определяется изменениями в БД, а не временем получения HTTP-запроса,
получения одной из блокировок или отметкой времени в теле вебхука.

### 4.3. Обоснование и компромисс

Политика сохраняет неизменность принятого решения. Пользователь не получает
готовый результат вместе с возвращёнными за эту же задачу токенами; уже
оформленный возврат не отменяется и не вызывает неожиданного нового списания.

Цена решения — возможная потеря пригодного позднего результата. Провайдер
может продолжать работу после нашего таймаута; протокол не обещает его отмену.
При переходе на следующую ногу фактически могут выполняться две генерации,
но сервис принимает результат только текущей активной попытки.

Альтернатива — принимать успех старой попытки, пока вся задача ещё активна.
Она требует дополнительных правил выбора победителя и завершения новой
попытки. Для задания выбираем окончательность закрытой попытки как более
простое и предсказуемое поведение.

### 4.4. Диагностика и проверка

Устаревшее событие логируется с `task_id`, `attempt_id`, провайдером,
`external_id` и причиной игнорирования. Его ссылка не публикуется как результат
задачи. Сохранённые статус, ошибка и время завершения попытки не переписываются.

Будущие тесты должны проверить:

- поздний успех после `failed` и возврата: результат отсутствует, возврат один;
- поздний успех старой попытки при активной следующей: новая попытка продолжает
  работу, финансовых изменений нет;
- поздний успех старой попытки после успеха следующей: результат следующей
  сохраняется;
- гонку успеха со сторожем в обоих порядках фиксации: применяется одно решение;
- успех после дедлайна до решения сторожа: успех принимается;
- повтор каждого из этих вебхуков: состояние и журнал остаются прежними.

Это поведение и его компромисс должны быть отражены в итоговом README.

## 5. Отправка и восстановление после падения

### 5.1. Сохранённое намерение и фоновые циклы

Строка попытки `pending` с неизменяемым `request_payload` является сохранённым
намерением отправить запрос. Она создаётся в той же транзакции, что задача
и списание, либо в транзакции перехода на следующую ногу. Отдельная таблица
очереди для этого задания не требуется.

В каждом из четырёх процессов могут работать циклы поиска `pending` и сторожа.
Они запускаются через lifespan приложения и периодически читают БД. В памяти
хранятся только текущие исполнения; список необходимой работы восстанавливается
из таблиц. Уведомление после `COMMIT` является ускорением, а периодический
поиск обеспечивает обнаружение работы после потери уведомления или рестарта.

После транзакции создания `POST /generate` вызывает тот же механизм отправки
первой попытки. Если другой исполнитель уже получил право на неё, повторный
HTTP-вызов не запускается. Ответ клиенту содержит сохранённый `task_id`;
продолжение работы не зависит от жизни этого HTTP-запроса.

### 5.2. Получение права на отправку

Исполнитель находит кандидата `pending`, затем в короткой транзакции получает
блокировки `users → generation_tasks → generation_attempts`. Фоновый поиск
использует `SKIP LOCKED` в этом порядке. Под блокировками проверяется, что
задача активна, попытка текущая, а действующего права другого исполнителя нет.

При первом захвате:

1. Записываем `sent_at` по времени БД и `deadline_at = sent_at + PROVIDER_TIMEOUT`.
   `sent_at` означает фиксацию начала отправки; HTTP-вызов ещё мог не состояться.
2. Создаём случайный `dispatch_token` и устанавливаем `dispatch_lease_until`.
3. Переводим задачу из `queued` в `processing`, оставляя попытку `pending`.
4. Фиксируем транзакцию, затем выполняем HTTP-запрос с сохранённым телом.

После истечения права другой исполнитель может захватить ту же попытку:
выдаётся новый `dispatch_token`, но сохраняются её UUID, тело запроса,
`sent_at` и `deadline_at`. Новая попытка и новое списание не создаются.
Прежний токен больше не даёт права сохранять ответ или ошибку отправки.

Если общий дедлайн уже истёк, новый HTTP-вызов не начинается: попытку завершает
сторож через `finish_attempt`. Право на отправку ограничивается меньшим
из двух сроков: текущий момент плюс `DISPATCH_LEASE` и общий `deadline_at`.

Начальные настройки: общий `HTTP_TIMEOUT = 5s`, `DISPATCH_LEASE = 15s`,
`PROVIDER_TIMEOUT = 60s`, интервал фонового поиска `1s`. Настройки должны
удовлетворять `HTTP_TIMEOUT < DISPATCH_LEASE < PROVIDER_TIMEOUT`.
`HTTP_TIMEOUT` ограничивает весь вызов, включая получение соединения и чтение
ответа; отдельные таймауты фаз HTTP-клиента не заменяют общий предел.

Истечение права не доказывает, что старый процесс остановился. Он может
продолжить HTTP-вызов после паузы. Токен защищает запись в БД от устаревшего
исполнителя, а дубликаты внешнего запроса устраняет контракт провайдера.

### 5.3. Идемпотентный контракт фейковых провайдеров

Запрос `POST /tasks` содержит сохранённое тело:

```json
{
  "client_attempt_id": "UUID попытки",
  "model_slug": "image-fast",
  "prompt": "Текст запроса",
  "ref_images": [],
  "callback_url": "http://api:8000/webhooks/providers/alpha"
}
```

Ключ идемпотентности — `(provider_name, client_attempt_id)`. При первом приёме
провайдер в одной транзакции сохраняет ключ, исходное тело, новый `external_id`,
сценарий поведения и обязанность подготовить результат. Только после фиксации
он возвращает `202 {"external_id": "..."}`.

Повтор с тем же ключом и тем же JSON-содержимым возвращает тот же `external_id`,
включая случай уже завершённой генерации. Новая генерация не создаётся,
готовый результат и сроки не пересчитываются. Сравнивается JSON-содержимое,
а не пробелы или порядок ключей при сериализации.

Повтор с тем же ключом и другим содержимым возвращает 409 без побочных
эффектов. Одновременные повторы координируются уникальным ограничением БД:
проигравший вставку читает сохранённую запись отдельным запросом и проверяет
содержимое. Предварительной проверки существования ключа недостаточно.

В тестовом проекте записи идемпотентности не удаляются автоматически.
Очистка всего тестового окружения допустима, потеря ключей при обычном
перезапуске провайдера — нет. Сохранённый `request_payload` основного сервиса
не меняется между отправками, включая `callback_url`.

Общий принцип ключа запроса и атомарного сохранения эффекта описан в
[AWS Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).
Конкретный контракт выше является нашим решением для фейковых провайдеров.

### 5.4. Сохранение ответа отправки

Получив `202`, исполнитель открывает новую транзакцию и снова получает
блокировки в общем порядке. Ответ применяется только если попытка остаётся
активной `pending`, токен совпадает с `dispatch_token`, а срок права ещё
не истёк по времени БД.

При соблюдении условий сохраняем `external_id`, переводим попытку
в `awaiting_result` и очищаем пару `dispatch_token`/`dispatch_lease_until`.
Общий `deadline_at` не продлевается. Если идентификатор уже известен,
он должен совпасть. Несовпадение является нарушением протокола.

Если вебхук уже завершил попытку или новый исполнитель сменил токен,
запоздалый ответ не переписывает данные. Если право истекло без смены токена,
ответ тоже не применяется: восстановитель сможет повторно получить его
идемпотентным запросом, пока не истёк общий дедлайн.

Наблюдаемая HTTP 5xx, ошибка соединения или таймаут передаются в `finish_attempt`
как `dispatch_error` с токеном. При актуальном токене это сразу ведёт на
следующую ногу или к возврату, как требует задание. Автоматические HTTP-повторы
таких ошибок отключены. Восстановительная отправка той же попытки нужна
после потери исполнителя или невозможности сохранить исход, а не вместо
правила перехода после уже обработанной ошибки.

Если процесс увидел HTTP-ошибку, но упал до её фиксации, этот факт остался
только в его памяти. Восстановитель действует по сохранённой `pending`
и может повторить тот же запрос. Окончательность решения относится к
зафиксированной транзакции, а не к потерянному локальному наблюдению.

Ошибка БД при сохранении `202` не считается отказом провайдера. При неизвестном
результате `COMMIT` состояние заново читается в новой транзакции. Если процесс
этого не сделал, восстановитель после истечения права увидит либо уже
сохранённое `awaiting_result`, либо `pending` для безопасного повтора.

Ответ 409 о несовпадении идемпотентного запроса логируется как нарушение
контракта; новый ключ для его обхода не создаётся. Он не превращается в
`payload`. Попытка остаётся доступной восстановлению до общего дедлайна,
после которого сторож применит таймаут.

### 5.5. Провайдер принял запрос, но `external_id` не сохранён

Критический сценарий обрабатывается так:

1. В основной БД уже сохранены UUID попытки, тело запроса и начатая отправка.
2. Провайдер сохраняет свою задачу с этим `client_attempt_id` и отвечает `202`.
3. Основной процесс падает до сохранения ответа. Попытка остаётся `pending`.
4. После истечения права восстановитель получает новый токен и отправляет
   то же тело с тем же `client_attempt_id`, если общий дедлайн ещё не истёк.
5. Провайдер возвращает прежний `external_id` без новой генерации.
6. Восстановитель сохраняет ответ по пункту 5.4. Если общий дедлайн истёк
   раньше, сторож окончательно закрывает попытку; её поздний результат
   обрабатывается по разделу 4.

Провайдер мог прислать вебхук и до шага 4. Поэтому каждое его событие содержит
`client_attempt_id`, `external_id`, статус и ссылку либо тип ошибки.
Все поля входят в сырое тело, подписанное HMAC-SHA256.

После проверки подписи адаптер находит попытку по `client_attempt_id`,
сверяет провайдера с именем в URL и записью попытки и вызывает `finish_attempt`.
У активной попытки ещё отсутствующий `external_id` сохраняется вместе
с результатом. Вебхук не обязан ждать восстановления ответа `202` и не зависит
от действительности токена отправителя. Поздний `202` после такого вебхука
не меняет завершённую попытку.

### 5.6. Восстановление фейкового провайдера и доставка вебхуков

При приёме новой задачи провайдер один раз выбирает задержку и сценарий
выполнения и сохраняет их. Фоновые циклы находят `accepted`, у которых
наступило время готовности. Под блокировкой строки сохраняются терминальный
исход, точные байты вебхука и время его доставки одной транзакцией.
Задержка не реализуется единственным `sleep` в памяти процесса.

Цикл доставки получает временный токен на строку провайдера и выполняет
HTTP-вызов после `COMMIT`. Отправляются сохранённые байты; `X-Signature`
вычисляется для этих же байтов. Успешная доставка отмечается отдельной
транзакцией только при совпадении ещё действующего токена доставки.

При падении после отправки, но до отметки доставки, право истечёт и событие
будет отправлено повторно. При ответе не-2xx или сетевой ошибке сохраняется
следующее время повтора с ограниченной задержкой. Событие не удаляется
до успешной доставки; конкретные интервалы задаются настройками.
Корректный поздний результат получает 2xx и прекращает повторную доставку.

Режимы тестирования также сохраняются в сценарии задачи провайдера:

- обычный результат готов через 2–20 секунд;
- двойной вебхук отправляет одинаковое сохранённое тело дважды, в том числе
  конкурентно; успешность пары отмечается после двух ответов 2xx;
- отсутствие вебхука намеренно отключает доставку для этой задачи;
- поздний результат задаёт задержку больше `PROVIDER_TIMEOUT`;
- синхронный 503 до приёма не создаёт задачу провайдера;
- таймаут ответа может возникать после сохранения задачи провайдера:
  обработчик задерживает ответ, но фоновая генерация уже сохраняется в БД.

Проверка существующего ключа идемпотентности предшествует применению сценария
нового запроса. Повтор уже принятой задачи возвращает прежний `202`,
не переигрывая синхронный отказ и не выбирая заново случайный исход.

### 5.7. Матрица восстановления

| Место падения | Что остаётся в БД | Что происходит после восстановления |
| --- | --- | --- |
| До фиксации создания генерации | Нет задачи, попытки и списания | Транзакция откатывается |
| После создания, до захвата отправки | Задача, списание, `pending` без токена | Фоновый исполнитель находит попытку |
| После захвата, до HTTP-вызова | `pending` с токеном и дедлайном | После истечения права другой исполнитель отправляет тот же запрос |
| После приёма провайдером, до сохранения `202` | Задача провайдера; у сервиса ещё `pending` | Повтор возвращает тот же `external_id` либо ранний вебхук завершает попытку |
| После сохранения `202` | `awaiting_result` с общим дедлайном | Принимается вебхук либо сторож применяет таймаут |
| Во время перехода на следующую ногу или возврата | Либо вся транзакция, либо ни одно её изменение | Повтор события или сторож применяет недостающее решение |
| После фиксации следующей `pending`, до уведомления исполнителя | Новая попытка уже сохранена | Её обнаруживает фоновый поиск |
| После финализации, до ответа на вебхук | Итог задачи и финансовые операции сохранены | Повтор подтверждается без изменения данных |
| Провайдер упал после приёма задачи | Сохранены ключ и сценарий | Генерация продолжается по сохранённому сроку |
| Провайдер упал после отправки вебхука, до отметки доставки | Событие остаётся недоставленным | Повторяется то же подписанное тело |

`pending` с `sent_at = NULL` ещё не начиналась и подхватывается исполнителем.
У начатой `pending` есть неизменяемый дедлайн: повторные падения и захваты
не продлевают ожидание бесконечно. Сторож закрывает такую попытку по тем же
правилам, что и молчащую `awaiting_result`, даже если её токен ещё заполнен.

### 5.8. Границы гарантий

Восстановление предполагает сохранность PostgreSQL и последующее возобновление
работы хотя бы одного исполнителя. Обычный перезапуск контейнеров сохраняет
том БД; удаление тома с данными не входит в гарантию восстановления.

Внутри сервиса финансовый эффект события защищён транзакциями и уникальными
ограничениями. HTTP-запросы и вебхуки могут доставляться повторно.
На стороне фейкового провайдера один ключ попытки создаёт не более одной
генерации благодаря его собственной сохранённой идемпотентности.

Это не гарантия одной внешней генерации на всю задачу: переходы между ногами
могут оставить предыдущего провайдера работающим. Отмена внешней работы
в контракт не входит. Итоговый результат и возврат регулируются разделом 4.

Если клиент потерял ответ `POST /generate`, созданная задача продолжит
выполняться. Повтор этого метода способен создать вторую задачу: ключ
идемпотентности клиентского API в задании не предусмотрен. Восстановление
сохранённой задачи и защита клиентского повтора являются разными гарантиями;
это ограничение следует явно указать в README.

### 5.9. Сценарии для проверки реализации

- Падение после списания до HTTP-вызова: попытка подхватывается, нового
  списания нет.
- Падение после приёма запроса провайдером до сохранения `external_id`:
  повтор возвращает прежний идентификатор, у провайдера одна генерация.
- Ранний вебхук завершает попытку без сохранённого `202`; поздний ответ
  отправки не меняет результат.
- Два исполнителя одновременно захватывают `pending`: действующий токен
  один. После его смены старый ответ и старая ошибка не применяются.
- Два конкурентных запроса провайдеру с одинаковым ключом дают один
  `external_id`; тот же ключ с другим телом даёт 409.
- При восстановительном повторе не меняются исходный запрос и общий дедлайн.
- Повторные падения до сохранения `202` не оставляют начатую `pending`
  бессрочно: сторож завершает её и выполняет fallback либо возврат.
- Перезапуск провайдера сохраняет ключ идемпотентности, сценарий и обязанность
  доставить вебхук; падение после доставки допускает безопасный дубль.
- Ошибка БД при сохранении `202` не превращается в отказ провайдера.
- Убийство одного из четырёх процессов после каждого значимого `COMMIT`
  не теряет сохранённую работу и не дублирует финансовый эффект.

Это план проверок будущей реализации. Тесты должны моделировать падение
исполнителя или процесса, а не только обычное исключение с корректной очисткой.
