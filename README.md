# Сервис генерации

Реализация [тестового задания](TASK.md) по [плану](PLAN.md)
и [архитектуре](docs/architecture.md). Готовы этапы 1–8: каркас, Docker Compose,
схема БД, финансовые операции, создание задачи, общий механизм завершения попытки,
фейковые провайдеры, отправка задач и фоновые процессы. HTTP-методы
предметного API будут подключены на этапе 9.

Используется Python 3.12. Зависимости описаны в `pyproject.toml`, точные
версии и хеши зафиксированы в `uv.lock`. Для управления окружением используется
[uv](https://docs.astral.sh/uv/) версии 0.13.5.

## Запуск через Docker

Достаточно Docker с Compose; локальные Python и uv не требуются.
Из каталога проекта выполните:

```powershell
docker compose up --build -d --wait
docker compose ps
```

Без `.env` используются значения для локальной разработки из `compose.yaml`.
Для изменения портов и настроек скопируйте `.env.example` в `.env`.

Сначала запускается PostgreSQL 17, затем одноразовые задания `db-bootstrap`
и `migrate` создают роли и применяют миграции. После их успешного завершения
стартуют API с четырьмя процессами Uvicorn, `alpha` и `beta`.
Завершение `db-bootstrap` и `migrate` с кодом 0 является штатным.
Все HTTP-приложения работают под непривилегированным
пользователем. API доступен по `http://localhost:8000`, документация — `/docs`.
Провайдеры доступны внутри сети Compose по `http://alpha:8000`
и `http://beta:8000`.

`GET /health/live` проверяет процесс. `GET /health/ready` выполняет `SELECT 1`
в PostgreSQL: при недоступности базы возвращается 503. Compose ждёт готовности
БД перед запуском приложений и проверяет готовность каждого компонента.

Данные PostgreSQL хранятся в именованном томе `postgres_data`, который
сохраняется при `docker compose down`. Порт БД на хосте — `127.0.0.1:55432`,
чтобы не конфликтовать с уже установленным PostgreSQL на 5432.
Порты меняются через `API_PORT` и `POSTGRES_PORT`.

В Compose адреса БД используют внутренний хост `db:5432` и `POSTGRES_DB`.
`POSTGRES_USER` и `POSTGRES_PASSWORD` используются только для административного
задания `db-bootstrap`. Пароли трёх отдельных ролей задаются через
`MIGRATION_DATABASE_PASSWORD`, `APP_DATABASE_PASSWORD`, `PROVIDER_DATABASE_PASSWORD`.
`DATABASE_URL` в `.env` предназначен для запуска Python на хосте.
Для локального примера используйте
в реквизитах БД буквы, цифры, дефисы и подчёркивания. При изменении реквизитов
обновите и локальный `DATABASE_URL`. Переменные `POSTGRES_*` инициализируют
только пустой том; изменение пароля в `.env` не меняет пароль в существующей БД.

Провайдеры принимают `POST /tasks`; сценарии сбоев и формат запроса описаны
в разделе «Фейковые провайдеры» ниже.

```powershell
docker compose logs api alpha beta
docker compose down
```

## Миграции и роли БД

Все таблицы создаются Alembic; приложение не вызывает `create_all()`.
`0001` создаёт семь таблиц основного сервиса и таблицу
`fake_providers.provider_tasks`, внешние ключи, проверки и индексы.
`0002` добавляет `alpha`, `beta`, модели `image-fast` (2 токена),
`video-long` (25 токенов), четыре ноги по заданию и права ролей.

Роли создаются повторяемой командой `db-bootstrap`; пароли берутся из окружения
и не хранятся в миграциях. Роль `generation_migrator` владеет таблицами.
`generation_app` читает каталог и добавляет финансовые операции, но не может
изменять или удалять журнал, каталог и сохранённый запрос попытки.
Роль `generation_provider` имеет доступ только к таблице в `fake_providers`.
Роли приложений не могут создавать таблицы приложения или переключаться на миграционную
роль. Для блокировки пользователей через `FOR UPDATE` основной роли отдельно
разрешён `UPDATE(id)`; прочие права обновления выдаются по служебным столбцам.
Часовой пояс подключений этих трёх ролей — UTC.

При обычном `docker compose up` миграции выполняются автоматически.
Повторное применение безопасно. Отдельные команды для уже запущенной БД:

```powershell
docker compose run --rm --no-deps migrate alembic current
docker compose run --rm --no-deps migrate alembic upgrade head
docker compose run --rm --no-deps migrate alembic check
```

Для добавления следующей миграции сначала измените SQLAlchemy-модели,
затем создайте ревизию с каталогом миграций, подключённым с хоста:

```powershell
docker compose build migrate
docker compose run --rm --no-deps --volume "${PWD}/migrations:/app/migrations" migrate alembic revision --autogenerate -m "Describe the change"
```

Проверьте сгенерированные `upgrade()` и `downgrade()`: данные каталога,
права, изменение CHECK-ограничений и создание схем требуют ручной проверки.
После добавления файла пересоберите образ и примените миграцию:

```powershell
docker compose build migrate
docker compose run --rm --no-deps migrate alembic upgrade head
docker compose run --rm --no-deps migrate alembic check
```

Откат выполняется через `alembic downgrade <revision>` под миграционной ролью.
Удаление начального каталога блокируется внешними ключами, если он уже
используется задачами; `CASCADE` для удаления истории не применяется.

## Тестовые пользователи

```powershell
docker compose --profile tools run --rm --build seed
```

Команда создаёт пользователей `1` (100 токенов) и `2` (50 токенов).
Начальные балансы оформляются записями `payment_credit` с идентификаторами
`demo:initial:user:1` и `demo:initial:user:2`. Повторный запуск не создаёт
повторных начислений и не восстанавливает потраченные токены. Конфликт
содержимого уже существующего начального платежа откатывает команду.
Без этой команды миграции создают каталог без демонстрационных пользователей.

## Тесты в Docker

```powershell
docker compose --profile test run --rm --build tests
```

Тестовый образ включает зависимости разработки. Команда запускает PostgreSQL
и выполняет тесты конфигурации, HTTP-проверок и готовности с настоящей БД.
Тесты схемы создают отдельные базы `test_schema_<uuid>`, применяют миграции,
проверяют ограничения, права и начальные данные, а затем удаляют эти базы.
Рабочая БД не очищается. Административные реквизиты передаются только
тестовому контейнеру для создания и удаления этих временных баз.
Без `TEST_DATABASE_URL` проверка готовности с PostgreSQL пропускается;
тесты схемы дополнительно требуют `TEST_ADMIN_DATABASE_URL`,
`TEST_MIGRATION_DATABASE_URL` и `TEST_PROVIDER_DATABASE_URL`.

## Финансовые операции

Операции находятся в `generation_service.services.finance`.
`FinancialService.credit_payment(PaymentEvent(...))` принимает событие оплаты:
`payment_id`, `user_id`, `tokens` и `status`. Статус `success` начисляет токены;
`pending` и `failed` не создают операций. Количество токенов — положительное
целое в диапазоне `BIGINT`; строки, дробные значения и `true` не принимаются.
Пустые идентификаторы оплаты отклоняются без обращения к БД.

`FinancialService.get_balance(user_id, history_limit=20)` возвращает полный
баланс и последние записи журнала из одного снимка `REPEATABLE READ`.
`history_limit` принимает значения от 1 до 100 и ограничивает только журнал.
У существующего пользователя без операций баланс равен нулю;
неизвестный пользователь вызывает `UserNotFound`.

`debit_generation(session, task_id)` и `refund_generation(session, task_id)`
работают в транзакции вызывающей операции и не выполняют `COMMIT`.
Создание задачи атомарно включает списание;
`finish_attempt` атомарно объединяет завершение задачи и возврат. Возврат разрешён
только для `failed` и рассчитывается по исходному списанию, согласованному
с зафиксированной ценой задачи. Возврат без списания отклоняется.

Каждая запись журнала предваряется блокировкой пользователя, а для генерации
также задачи, в порядке `users → generation_tasks`. Уже удерживаемые этой
транзакцией блокировки можно получать повторно. Баланс перед новым списанием
читается отдельным запросом после получения блокировки. Поэтому конкурентные
списания видят результат предыдущего списания и не расходуют одни токены дважды.
Команда демонстрационных пользователей также соблюдает этот порядок.

Однократность финансового эффекта обеспечивается совместно:

- `UNIQUE(payment_id)` и `UNIQUE(task_id, kind)` в PostgreSQL;
- `INSERT ... ON CONFLICT DO NOTHING` и проверкой содержимого существующей записи;
- общими блокировками пользователя и атомарной транзакцией всей операции.

Совпадающий повтор возвращает прежнюю запись с `applied=False`.
Одинаковый идентификатор оплаты с другим пользователем или суммой вызывает
`PaymentConflict`; несовпадение существующего списания или возврата —
`LedgerIntegrityError`. Ошибка откатывает всю внешнюю транзакцию.
Если процесс упал до фиксации, PostgreSQL откатывает изменения; после фиксации
повтор с тем же идентификатором обнаруживает уже записанный эффект.

`TransactionRunner` создаёт отдельную `AsyncSession` на операцию, ограничивает
ожидание блокировки пятью секундами и возвращает результат после `COMMIT`.
Ошибки PostgreSQL `40P01` и `40001` вызывают ограниченный повтор всей
транзакции, максимум три попытки с повторным чтением данных. Потеря соединения,
таймаут блокировки и исчерпание повторов дают `DatabaseUnavailable`.
Неизвестный результат `COMMIT` автоматически не переигрывается. Код внутри
повторяемой транзакции должен выполнять только операции с БД, без HTTP-вызовов.
HTTP-обработка этих ошибок и проверка HMAC будут подключены на этапе 9.

Тесты финансов используют отдельные временные БД и подключения роли приложения:
20 конкурентных повторов оплаты, повторы списаний, 10 возвратов, конкуренцию
за остаток баланса, конфликты идентификаторов, откат составных операций,
согласованное чтение, таймауты и повторы транзакций. Отдельная проверка запускает
четыре процесса, каждый доставляет одну оплату пять раз: создаётся одно начисление.

## Создание задачи

`GenerationService` из `generation_service.services.generation` принимает
`TransactionRunner` и базовый адрес обратного вызова. Для приложения передавайте
`str(settings.callback_base_url)`; значение `CALLBACK_BASE_URL` по умолчанию —
`http://api:8000`. Допустим HTTP/HTTPS-адрес с префиксом пути, без query и fragment.
Провайдер должен видеть этот адрес из своей сети. Для API, запущенного на хосте
при провайдерах в Docker Desktop, можно использовать `http://host.docker.internal:8000`.

```python
service = GenerationService(transactions, str(settings.callback_base_url))
result = await service.create(GenerationRequest(
    user_id=1,
    model_slug="image-fast",
    prompt="Нарисуй море",
    ref_images=[],
))
task_id = result.task_id
```

Запрос строго проверяет целый `user_id`, непустые строки `model_slug` и `prompt`,
массив непустых строк референсов. Референсы можно опустить; тогда их список пуст.
Неизвестные поля, включая переданную клиентом цену, отклоняются.
Модель запроса неизменяема и сохраняет копию референсов для повторов транзакции.

Операция выбирает первую по приоритету ногу, принимающую все референсы.
Затем под блокировкой пользователя проверяет баланс и число задач в `queued`
и `processing`. Лимит — три активные задачи; завершённые задачи его не занимают.
Недостаточный баланс имеет приоритет перед превышением лимита.
Ошибки представлены `ModelNotFound`, `UnsupportedReferences`, `UserNotFound`,
`InsufficientFunds` и `ActiveTaskLimit`; HTTP-ответы подключаются на этапе 9.

Одна транзакция сохраняет `queued`-задачу с ценой из каталога, единственное
списание и первую попытку `pending`. Попытка содержит UUID, исходный prompt,
референсы, имя модели и callback URL `/webhooks/providers/{name}`.
До отправки `sent_at`, `deadline_at`, `external_id` и право отправителя пусты.
HTTP-отправку выполняет `DispatchService`. Ошибка любого шага создания откатывает все записи;
результат возвращается после `COMMIT`.

Повтор клиентского запроса создаёт отдельную задачу и новое списание при
соблюдении баланса и лимита: идемпотентность `POST /generate` заданием не предусмотрена.
При неизвестном результате `COMMIT` автоматический повтор запрещён.

## Завершение попытки и поздний результат

`AttemptService(transactions).finish_attempt(FinishCommand(...))` из
`generation_service.services.attempts` обрабатывает все источники одним путём:

- `provider_webhook`: `completed` с непустым `result_url` либо `failed` с
  `error_type` из `technical`, `moderation`, `payload`; `external_id` обязателен;
- `dispatch_error`: `failed/technical` с актуальным `dispatch_token`;
- `watchdog`: `timeout`, если дедлайн начатой попытки истёк по времени БД.

Команда указывает конкретную попытку и провайдера. Это внутренний контракт;
подпись HMAC и HTTP-адаптеры будут подключены на этапе 9. Ранний достоверный
вебхук для уже начатой `pending` может завершить попытку до сохранения `202`:
его `external_id` сохраняется в той же транзакции. Несовпадение провайдера
или внешнего идентификатора является ошибкой события, включая повторы
для закрытых попыток. Неначатая `pending` не завершается вебхуком.

Операция блокирует `users → generation_tasks → generation_attempts` и заново
проверяет состояния, дедлайн и право отправителя. Затем проверяет исходное
списание и отсутствие возврата у активной задачи. Все переходы выполняются
в одной транзакции; сетевых вызовов внутри неё нет.

`technical`, ошибка отправки и таймаут выбирают следующую ещё не использованную
ногу по приоритету и количеству референсов. `moderation` дополнительно исключает
ноги с `skip_on_moderation`; учитывается последний фактический отказ, поэтому
следующий `technical` снимает этот фильтр. `payload` завершает задачу сразу.
Если продолжение невозможно, задача получает `failed` и один полный возврат.

Перед вставкой следующей попытки старая закрывается, а её токен отправителя
очищается. Исходные сроки и запрос сохраняются в истории. Новая `pending`
получает свой UUID и номер; prompt, модель и референсы копируются из сохранённого
запроса, в callback URL меняется имя провайдера с сохранением префикса адреса.
Задача переходит в `queued`; дополнительного списания нет.

Результат возвращается после `COMMIT`: `completed`, `next_attempt_created`
(с `next_attempt_id`), `failed_refunded`, `ignored` с причиной либо `deferred`.
Для сторожа `skip_locked=True` пропускает занятую строку на любом уровне,
освобождает уже полученные блокировки и возвращает `deferred` без изменений.
Ошибки целостности и записи откатывают также статусы задачи и попытки.

Первое допустимое завершение, зафиксированное под блокировками, окончательно.
Поздний корректный `completed` или `failed` закрытой попытки даёт `ignored`:
он не меняет результат, историю или журнал, даже если новая попытка ещё активна.
HTTP-адаптер должен подтвердить такое корректное событие ответом 2xx.
Если дедлайн уже наступил, но сторож ещё не зафиксировал таймаут, успех
активной попытки принимается. Принятый успех исключает последующий возврат.
Так пользователь не получает одновременно результат и возвращённые токены;
компромисс — потеря пригодного результата, пришедшего после закрытия попытки.
Причина игнорирования и идентификаторы доступны в INFO-логе модуля.

Дедлайны и срок права отправителя проверяются по `clock_timestamp()` под
блокировками. Общее время завершения задачи и попытки не предшествует их
созданию, в том числе при коррекции часов сервера назад; такая коррекция
не подменяет реальное время при проверке дедлайна или права отправки.

Проверки включают ранние и поздние вебхуки, гонки исходов, модерацию нескольких
ног, повторные возвраты из четырёх процессов, пропуск каждой из блокировок
сторожем, ошибки финансовой основы и откат при ошибке возврата или новой попытки.

## Фейковые провайдеры

`alpha` и `beta` принимают `POST /tasks` и после фиксации в PostgreSQL
возвращают `202 {"external_id":"..."}`. Пример тела:

```json
{
  "client_attempt_id": "dfd42f44-404f-4ec4-95fe-6bf96d718038",
  "model_slug": "image-fast",
  "prompt": "Нарисуй море",
  "ref_images": [],
  "callback_url": "http://api:8000/webhooks/providers/alpha"
}
```

UUID задаётся канонической строкой. Все пять полей обязательны; неизвестные
поля и некорректные значения дают 422. Один ключ `(provider_name, client_attempt_id)`
создаёт одну генерацию. Повтор с тем же JSON возвращает прежний `external_id`,
включая завершённые задачи; порядок ключей и форматирование JSON не влияют.
Другие значения любого поля с тем же ключом дают 409 без изменений.
Проверка повтора предшествует синхронному отказу и выбору сценария.
Недоступность БД даёт 503; ответ 202 никогда не предшествует `COMMIT`.

В Compose настройки каждого провайдера имеют префикс `ALPHA_` или `BETA_`.
Например, `ALPHA_FAILURE_RATE=1` и `ALPHA_FAILURE_TYPE=moderation` заставляют
новые задачи alpha завершаться отказом по модерации. Изменения `.env`
применяются командой `docker compose up -d alpha beta`.
При прямом запуске Python используются имена из таблицы без префикса,
а также `PROVIDER_NAME`, `PROVIDER_WEBHOOK_SECRET` и `DATABASE_URL` роли
`generation_provider`.

| Настройка без префикса | По умолчанию | Поведение |
| --- | --- | --- |
| `FAILURE_RATE` | `0` | Доля отказов от 0 до 1 |
| `FAILURE_TYPE` | `technical` | `technical`, `moderation` или `payload` |
| `SYNC_MODE` | `none` | `none`, `503` до приёма либо `timeout` после приёма |
| `RESPONSE_DELAY` | `10` | Задержка ответа при `timeout`; задайте больше `HTTP_TIMEOUT` основного сервиса |
| `DELAY_MIN`, `DELAY_MAX` | `2`, `20` | Границы случайной задержки генерации, в секундах; для тестов допустим 0 |
| `DUPLICATE_WEBHOOK` | `false` | Требовать две успешные доставки одного тела |
| `CONCURRENT_DUPLICATES` | `false` | Отправить дубликаты одновременно |
| `NO_WEBHOOK` | `false` | Сохранить результат, намеренно отключив доставку |
| `LATE_COMPLETED` | `false` | Принудительный успех, даже при `FAILURE_RATE=1`, с задержкой `LATE_DELAY` |
| `LATE_DELAY` | `65` | При включённом позднем успехе строго больше общего `PROVIDER_TIMEOUT` (60 по умолчанию) |
| `POLL_INTERVAL` | `1` | Пауза фоновых циклов, когда работы нет или произошла ошибка |
| `WEBHOOK_TIMEOUT` | `5` | Общий срок HTTP-доставки, включая последовательную пару |
| `DELIVERY_LEASE` | `15` | Срок токена доставки; строго больше `WEBHOOK_TIMEOUT` |
| `RETRY_INTERVAL` | `5` | Пауза до повтора неуспешной доставки, больше 0 и не более 60 секунд |

Сценарий, выбранный при приёме, и срок готовности сохраняются в БД:
смена настроек и перезапуск не выбирают результат заново. Режим `timeout`
задерживает только первый ответ после сохранения; генерация продолжается,
а повтор того же запроса отвечает сразу. Режим 503 не сохраняет новую задачу.

Фоновые циклы под блокировкой строки сохраняют результат и точные байты
вебхука одной транзакцией. Успешное событие содержит `client_attempt_id`,
`external_id`, `status="completed"`, `result_url`; отказ — те же идентификаторы,
`status="failed"`, `error_type`. Ссылка имитирует файл и не требует хранилища.
`X-Signature` — hex HMAC-SHA256 сохранённых байтов с секретом соответствующего
провайдера; отправляется `Content-Type: application/json`.

Доставка получает токен и срок действия в БД, затем выполняет HTTP вне
транзакции. Только 2xx считается успехом; редиректы не выполняются.
Сетевые ошибки и остальные ответы оставляют событие для повторов без лимита
числа попыток. При двойном вебхуке подтверждаются две доставки; если одна
не удалась, повторяется оставшаяся. При падении после отправки, до записи
подтверждения, событие повторяется после истечения токена теми же байтами.
Устаревший исполнитель не может подтвердить доставку. Записи и ключи
идемпотентности сохраняются и после успеха. Несколько процессов используют
блокировки PostgreSQL и `SKIP LOCKED`.

Сейчас основной сервис ещё не принимает эти вебхуки: HTTP-адаптер будет
подключён на этапе 9. До этого callback на API получает 404 и остаётся
в очереди повторов. Основной сервис уже отправляет сохранённые `pending`
и обрабатывает отсутствие результата через сторож.

Тесты провайдеров используют временную PostgreSQL, четыре независимых процесса,
реальную HTTP-доставку и принудительное завершение процесса между отправкой
и подтверждением. Рабочая БД при этих проверках не изменяется.

## Отправка, восстановление и сторож

В каждом из четырёх процессов API через lifespan запускаются два фоновых
цикла: отправка `pending` и проверка дедлайнов. Источник работы — PostgreSQL;
дополнительный брокер и очередь в памяти не требуются. При перезапуске циклы
снова находят незавершённые попытки. Пауза при отсутствии работы или ошибке —
`POLL_INTERVAL` (по умолчанию 1 секунда). При завершении приложения циклы
отменяются до закрытия HTTP-клиента и пула БД; незавершённая работа остаётся
доступной восстановлению.

`DispatchService(transactions, settings)` находится в
`generation_service.services.dispatch`. `dispatch(attempt_id, client)` отправляет
конкретную попытку, `dispatch_next(client)` находит следующую доступную.
Оба метода используют один механизм захвата. HTTP-адаптер этапа 9 сможет
вызвать `app.state.dispatch.dispatch(attempt_id, app.state.http_client)` после
сохранения задачи; периодический поиск обеспечивает отправку и без этого вызова.

Захват выполняется в короткой транзакции с порядком блокировок
`users → generation_tasks → generation_attempts`. Фоновый поиск пропускает
занятые строки через `SKIP LOCKED` и продолжает следующие страницы кандидатов.
Под блокировками заново проверяются состояния, токен и дедлайн.
Первый захват сохраняет `sent_at`, общий `deadline_at`, случайный токен,
срок права на отправку и переводит задачу в `processing`. Только после
`COMMIT` выполняется `POST /tasks` с неизменяемым сохранённым JSON.

Настройки интервалов: `HTTP_TIMEOUT=5`, `DISPATCH_LEASE=15`,
`PROVIDER_TIMEOUT=60`; требуется
`HTTP_TIMEOUT < DISPATCH_LEASE < PROVIDER_TIMEOUT`.
Право ограничено общим дедлайном. Перед HTTP дополнительно проверяется
действительность токена; общий предел вызова ограничивает получение соединения,
отправку и чтение всего ответа, а также оставшееся время права на отправку.
Редиректы и автоматические HTTP-повторы отключены. `ALPHA_URL` и `BETA_URL`
задают базовые адреса провайдеров, допускающие префикс пути; к ним добавляется `/tasks`.

Корректный `202` с непустым строковым `external_id` сохраняется новой
транзакцией под теми же блокировками: попытка становится `awaiting_result`,
токен очищается. Сохранение допустимо только для активной `pending` с прежним
ещё действующим токеном. Ранний вебхук, истечение права или захват другим
исполнителем делают старый ответ неприменимым. Дедлайн не продлевается.
Ответы 202 ограничены 64 КиБ; ошибочная структура считается нарушением протокола.

Наблюдаемый 5xx, ошибка соединения или HTTP-таймаут передаются в
`finish_attempt` как `dispatch_error/technical` с токеном. Это сразу закрывает
попытку и создаёт следующую либо единственный возврат. Следующая сохранённая
`pending` обнаруживается тем же циклом. Даже если провайдер успел принять
запрос до таймаута, его поздний результат закрытой попытки игнорируется.
409, прочие неожиданные ответы и неверный `external_id` логируются как ошибки
протокола: ключ не заменяется, `payload` не выставляется, попытка остаётся
для восстановления до общего дедлайна.

При потере процесса после приёма запроса провайдером попытка остаётся `pending`.
После истечения права новый исполнитель выдаёт новый токен, сохраняя UUID,
тело, `sent_at` и исходный дедлайн. Повторный HTTP возвращает тот же
`external_id` благодаря идемпотентности провайдера. Прежний исполнитель
больше не может сохранить ответ или ошибку. Если общий дедлайн уже истёк,
повторная отправка не начинается.

Ошибка БД при записи ответа не превращается в отказ провайдера. При неизвестном
результате `COMMIT` следующий поиск обнаружит либо уже сохранённую
`awaiting_result`, либо `pending`, доступную восстановлению после истечения
права. Дополнительного списания и новой внешней генерации при восстановлении нет.

`WatchdogService.run_once()` ищет начатые `pending` и `awaiting_result`
с истёкшим `deadline_at` и вызывает тот же `finish_attempt` с
`source="watchdog"`, `outcome="timeout"`, `skip_locked=True`. Время и состояние
снова проверяются под блокировками. Занятые строки не задерживают обработку
остальных; конкурентные сторожа не дублируют следующую попытку или возврат.
Неначатые `pending` без дедлайна сторож не завершает.

Тесты проверяют конкурентные захваты и ответы, пропуск каждого уровня
блокировок, сохранение дедлайна, ошибки HTTP и БД, ранний вебхук, четыре
процесса отправки и сторожа, принудительное падение после фиксации у провайдера
и работу lifespan с реальным HTTP. HTTP-приём вебхуков основным сервисом
по-прежнему относится к этапу 9.

## Локальная разработка

Скопируйте `.env.example` в `.env` и настройте адрес PostgreSQL и секреты.
`.env` исключён из Git. Примеры секретов предназначены для локального запуска.

```powershell
Copy-Item .env.example .env
uv sync --locked
uv run --locked uvicorn generation_service.main:app --host 0.0.0.0 --port 8000 --workers 4
```

Проверка процесса: `GET http://localhost:8000/health/live`.
OpenAPI: `http://localhost:8000/docs`.

Для локального приложения сначала выполните `docker compose up -d migrate`.
Если локально запускаются и провайдеры, замените `ALPHA_URL` и `BETA_URL`
на их адреса на хосте. Обычный локальный запуск API использует ту же БД,
что контейнеры, и требует свободного порта 8000.

```powershell
uv run --locked pytest
```

Настройки читаются из окружения и `.env`; окружение имеет приоритет.
`DATABASE_URL` должен использовать драйвер `postgresql+asyncpg`.
Секреты обязательны. Интервалы задаются в секундах и проверяются при запуске:
`HTTP_TIMEOUT < DISPATCH_LEASE < PROVIDER_TIMEOUT`.

Для обновления зависимостей после изменения `pyproject.toml` выполните
`uv lock`, проверьте изменения `uv.lock` и повторите тесты.
